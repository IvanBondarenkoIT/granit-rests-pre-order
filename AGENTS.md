# AGENTS.md — правила разработки (granit-rests-pre-order)

## 0. Перед каждым изменением
1. Прочитать этот файл, `docs/ROADMAP.md` (если есть), `docs/DB_SCHEMA.md` и `docs/CRITICAL_PRODUCTS.md`.
2. Свериться с текущим этапом; не выходить за рамки согласованного шага.
3. Открытые вопросы — в `docs/REQUIREMENTS_WORKSHEET.md`; не «додумывать» бизнес-логику молча.

## 1. Язык и общение
- Документация, коммиты и пояснения — на русском.
- Код, имена идентификаторов — на английском.

## 2. Окружение
- Python 3.11 (совместимо с `fdb`; НЕ 3.13). Локальный `.venv`.
- Все зависимости — в `requirements.txt` с версиями.
- Локальная копия БД — Firebird 2.5 (ODS 11), читается через FB 2.5 embedded (`tools/fb25/fbembed.dll`).

## 3. Безопасность и секреты (must-have)
- НИКОГДА не хардкодить креды/токены/URL: только через `.env` (+ `.env.example` без секретов).
- `.env`, `data/`, `tools/`, `granit bd copy/`, кэши — в `.gitignore`.
- Доступ к Firebird — ТОЛЬКО read-only (`SELECT`/`WITH`). Никаких изменений боевой БД.

## 4. Работа с БД
- Источник истории — локальная копия `.GDB` (offline). Инкремент — опц. через Proxy API.
- Все запросы к Firebird — параметризованные (`?`), без конкатенации значений.
- Тяжёлые выборки — чанками/по нужным товарам; кэшировать.
- SQL хранить в `src/source/queries.py` с комментариями.
- Канонические правила домена:
  - продажи: `STORZAKAZDT.CSDTKTHBID IN (1,2,3,5)`, **все точки**;
  - остаток = нарастающая сумма `GDDKT.QUANT` по дате `DGVKT.DAT_`, **по всей компании**;
  - страховой запас = `GOODS.SQNT`; `target_qty` в списке критических = типичная партия заказа;
  - кофе (кг): параметр «Продукция» = «Кофе(кг)» (`GDSPARAMGDSREF` PARAMID=2, FIXVAL=3);
  - валюта закупки: GEL (₾), цена из приходов `GDDKT.PRICE`.

## 5. Структура и стиль кода
- Слои: `src/source` / `src/storage` / `src/etl` / `src/analysis` / `src/web` — независимы.
- Типизация (type hints), докстринги у публичных функций; без «мусорных» комментариев.
- Конфигурация — через `src/config.py` (чтение `.env`).
- Локальное хранилище — через SQLAlchemy (`DATABASE_URL`); цель — PostgreSQL, fallback — SQLite.

## 6. Данные и воспроизводимость
- Бизнес-метрики (расход, дата заказа) — задокументированы формулой в коде/доках.
- Фиксировать период/параметры расчёта.

## 7. Git
- Małые осмысленные коммиты на русском («зачем»). Не пушить без явной просьбы.

## 8. Качество и тестирование на каждом этапе
- **Не переходить к следующему этапу**, пока не пройден чеклист текущего (см. `docs/TESTING.md`).
- **Автотесты:** `PYTHONPATH=. pytest tests -q` — все зелёные.
- **Расчёты:** сверка эталона `DLSC002` (`GOODS.ID=24227`) — `python -m src.analysis.recommend` без регрессий по ключевым полям (ROP, дата заказа, qty).
- **Данные:** при изменении ETL/SQL — smoke `python -m src.etl.run_etl` + проверка строк в SQLite (`products`, `weekly_demand`).
- **GUI:** после каждой UI-фазы — ручной smoke по чеклисту в `docs/TESTING.md` (Обзор / Товар / Заказ).
- Новая расчётная логика → юнит-тест в `tests/` (минимум happy-path + один edge).
- Прогон линтера/тестов перед коммитом.
