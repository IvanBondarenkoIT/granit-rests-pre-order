Ограниченный список для анализа (чтобы не гонять все ~10k товаров).

**Числа в колонке «Ориентир»** — типичный объём **последнего заказа** (партия, которую обычно заказываем), не `GOODS.SQNT` и не текущий остаток. Подтверждено 2026-06-25.

Сопоставление выполнено через локальную копию `GEORGIA.GDB` и Proxy API (`GOODS.ID` совпадают).

Статусы: ✅ найден · ⚠️ агрегат/уточнить · ❌ не найден.

Тип: **SKU** — конкретный товар (`GOODS.ID`); **GROUP** — агрегат по группе товаров (`GOODSGROUPS.ID`).

> **Страх.остаток на скрине:** формат «300/0/3» — для расчётов берём **первое число** = `GOODS.SQNT` (подтверждено: 300.00 = 300 у DLSC002).

## Детали по агрегатам

### Bag paper — особый случай (2026-06-25)
- Раздаётся **бесплатно** с кофе → в `STORZAKAZDT` почти нет продаж (сигнал спроса пустой).
- **План расчёта:** по **приходам** в `GDDKT` (всплески `inflow`): интервал между заказами и объём партии → **удельный расход** (шт/нед), далее прогноз как у остальных. Запасной вариант — дефолт из ориентира 300 шт и типичного интервала заказа.

### Coffee (1700 kg) — признак «Продукция = Кофе(кг)»
Канонический отбор кофе в **килограммах** (не по группам GOODSGROUPS):
- `GDSPARAMPRM.ID = 2`, имя **«Продукция»**
- `GDSPARAMVAL.ID = 3`, значение **«Кофе(кг)»**
- Связь: `GDSPARAMGDSREF` где `PARAMID = 2` и `FIXVAL = 3` → **~96 SKU**

В ETL агрегат Coffee собирается по параметру «Продукция»=«Кофе(кг)» (`FIXVAL=3`, ~96 SKU), **одной строкой** (сумма кг).

### Caotina (250 kg) — группа `Caotina ... (package)` (ID 22939)
Все фасовки Caotina (0,1 / 0,2 / 0,35 / 0,5 / 1 kg, sticks) висят на OWNER 22939. Агрегат = сумма SKU группы 22939.
